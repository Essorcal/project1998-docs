FrameReader drops a connection whose unframed buffer exceeds one maximum frame or whose head byte is not 0xAA (PR #220, follow-up 1 of the PR #213 review)

  • A connection whose head byte is not 0xAA after framing is dropped with one warning line naming the peer and the byte; it used to stall its inbound half forever. Frames parsed from the same read are delivered first.
  • The unframed buffer is capped at one maximum legal frame (65,538 bytes) before and after the handshake; it had no bound.
  • Both front doors get both rules through the one shared read loop; the session files did not change.
  • An HTTP request to the login port is now dropped on its first read instead of holding a slot for the 15 s handshake timeout. The game port's status probe is unaffected.
  • Drop was chosen over re-sync: the framing has no checksum or trailer and bodies are ciphered, so a forward scan can lock onto a false header.
  • While the head-byte rule stands the byte cap cannot fire; the cap states the bound in one place for the day re-sync is ever added. Stated in the code and the PR.
  • Six facts, one of them the boundary case that a maximum-length frame in 4 KB reads never trips the cap.
  • Protocol.md's hardening section records the two bounds.

A frame whose length field is under 2 is malformed: TryParse never throws and the reader drops the peer (PR #222, follow-up of PR #220)

  • A peer sending a frame whose length field is 0 or 1 is dropped with one warning line; it used to throw out of the read loop and log an error with a stack trace on the game side, one per connection.
  • TkPacket gains a minimum length of 2, a Parse that reports frame, need-more or malformed and never throws, and TryParse stays as a wrapper for its ten existing callers.
  • Frames ahead of the malformed one in the same read are delivered first; the status probe still wins.
  • With wire logging on, the "buffered/unframed" line prints the first 256 bytes and the total size instead of the whole buffer each read; one bad connection used to write over 2 MB of hex for a 65 KB stream.
  • Eleven new facts; the review ran an exhaustive parser probe over every u16 length value with no throw.
  • Protocol.md's framing section records the length floor.

The concurrency tests wait on progress, not on a fixed join (PR #221, follow-up of PR #216)

  • Seventeen facts timed on base and head, no median slower; whole-suite wall time fell about 8 s in Debug and 12 s in Release.

The tile translation facts and the content reload fact run in one collection (PR #223)

  • TileTranslationTests and ContentReloadTests share one xUnit collection, so the tile facts can no longer read the one-row stub table the reload fact publishes through the process-wide tile-map environment variable.
